# 1. Архитектурный фундамент Django и паттерн MVT

Веб-фреймворк Django реализует архитектурный паттерн **MVT (Model-View-Template)**, являющийся практической адаптацией классического шаблона проектирования **MVC (Model-View-Controller)** для веб-приложений.

```
 Пользователь (Браузер)
      │ ▲
      │ │ 6. Итоговый HTTP-ответ (HTML + CSS)
      ▼ │
┌────────────────────────────────────────────────────────┐
│                        DJANGO                          │
│                                                        │
│  1. WSGI / ASGI Handler (wsgi.py)                      │
│     Точка входа, преобразует сетевой поток в объект    │
│     запроса HttpRequest                                │
│            │                                           │
│            ▼                                           │
│  2. MIDDLEWARE (Слой промежуточной обработки)          │
│     Сессии, безопасность, аутентификация, CSRF-защита  │
│            │                                           │
│            ▼                                           │
│  3. URLconf (urls.py)                                  │
│     Диспетчер маршрутов: сопоставляет URL с View       │
│            │                                           │
│            ▼                                           │
│  4. View (views.py) ── [Контроллер бизнес-логики]      │
│            │                             ▲             │
│            │ Запрос данных               │ Данные      │
│            ▼                             │             │
│     Model (models.py) ◄──────────────────┘             │
│     Django ORM (Object-Relational Mapping) ── SQLite   │
│            │                                           │
│            │ Передача контекста (context dict)         │
│            ▼                                           │
│  5. Template Engine (templates/*.html)                 │
│     Рендеринг HTML с подстановкой переменных (DTL)     │
└────────────────────────────────────────────────────────┘
```

### Сравнение терминологии Django и классического MVC:

| Компонент в Django | Аналог в классическом MVC | Роль и назначение в проекте «Design.pro» |
| :--- | :--- | :--- |
| **Model** (`models.py`) | **Model** (Модель) | Схема реляционных данных, таблицы базы данных SQLite, ограничения полей (`max_length`, `unique`), валидаторы файлов на уровне сущностей и ORM-запросы. |
| **View** (`views.py`) | **Controller** (Контроллер) | Принимает объект запроса `HttpRequest`, проверяет права доступа (гость, клиент, админ), обрабатывает входящие формы, вызывает методы моделей, решает, какой HTTP-ответ вернуть (`render` или `redirect`). |
| **Template** (`templates/`) | **View** (Представление) | Пользовательский интерфейс: HTML-разметка страниц с вкраплениями тегов шаблонизатора Django Template Language (DTL), стили CSS и элементы форм. |

### Полный жизненный цикл HTTP-запроса (Пошаговый разбор):

Рассмотрим, что происходит под капотом веб-сервера, когда авторизованный пользователь открывает страницу своего личного кабинета `http://localhost:8089/cabinet/`:

1. **Инициация:** Пользователь вводит адрес в браузере или кликает по ссылке «Мои заявки». Браузер формирует HTTP GET-пакет и отправляет его на порт 8089.
2. **Точка входа (WSGI):** Сетевой сервер разработки Django принимает TCP-соединение и передает поток байтов в интерфейс `wsgi.py`. WSGI-обработчик парсит заголовки, параметры и тело запроса, создавая стандартный объект Python — `HttpRequest`.
3. **Конвейер Middleware (Сквозная фильтрация):** Объект `request` последовательно проходит через цепочку промежуточных обработчиков:
   - `SessionMiddleware`: извлекает из cookies идентификатор `sessionid`, находит в таблице `django_session` данные сессии и прикрепляет к объекту запроса словарь `request.session`.
   - `AuthenticationMiddleware`: считывает ID пользователя из сессии, находит соответствующую запись в таблице `catalog_user` и записывает объект пользователя в `request.user`. Если пользователь не авторизован, записывается `AnonymousUser`.
   - `CsrfViewMiddleware`: при GET-запросах пропускает поток дальше; при POST-запросах проверяет наличие корректного токена безопасности.
4. **Маршрутизация (URLconf):** Django обращается к корневому файлу `design_studio/urls.py`, который делегирует поиск в приложение `catalog/urls.py`. Диспетчер маршрутов находит совпадение пути `cabinet/` с именем функции `views.cabinet_view`.
5. **Проверка прав доступа (Декоратор):** Функция защищена декоратором `@login_required`. Декоратор проверяет флаг `request.user.is_authenticated`. Если запрос пришел от гостя — выполнение контроллера немедленно прерывается, и возвращается `HTTP 302 Redirect` на страницу авторизации `/login/?next=/cabinet/`.
6. **Выполнение бизнес-логики контроллера:** Внутри `cabinet_view`:
   - Формируется базовый QuerySet: `Application.objects.filter(user=request.user).select_related('category')`.
   - Происходит подсчет статистики для кнопок-фильтров (`.count()`).
   - Считывается GET-параметр `status` (если пользователь выбрал конкретный фильтр).
   - Применяется сортировка от свежих заявок к старым (`.order_by('-created_at')`).
7. **Работа Django ORM:** ORM транслирует методы Python в оптимизированный SQL-запрос с объединением таблиц `INNER JOIN`:
   ```sql
   SELECT catalog_application.*, catalog_category.*
   FROM catalog_application
   INNER JOIN catalog_category ON (catalog_application.category_id = catalog_category.id)
   WHERE catalog_application.user_id = 1
   ORDER BY catalog_application.created_at DESC;
   ```
8. **Рендеринг шаблона (DTL):** Контроллер вызывает `render(request, 'catalog/cabinet.html', context)`. Движок шаблонизации DTL берет базовый макет `base.html`, подставляет в блок `{% block content %}` верстку кабинета, выполняет цикл `{% for app in applications %}` и генерирует чистую итоговую HTML-страницу.
9. **Формирование ответа:** Создается объект `HttpResponse` со статусом `200 OK`, заголовком `Content-Type: text/html; charset=utf-8` и готовым телом HTML.
10. **Обратный путь и отображение:** Ответ проходит обратно через Middleware, передается через WSGI браузеру, который отрисовывает страницу со списком заявок и стилями `style.css`.

#### Конечный автомат (Finite State Machine) заявки:
Заявка на дизайн подчиняется строгой диаграмме состояний:

```
                   ┌─────────────────┐
                   │  [1] «Новая»    │ (создается клиентом автоматически)
                   └────────┬────────┘
                            │
            ┌───────────────┴───────────────┐
            │                               │
(действие админа с комментарием)    (действие админа с файлом дизайна)
            │                               │
            ▼                               ▼
┌───────────────────────┐       ┌───────────────────────┐
│ [2] «Принято в работу»│       │   [3] «Выполнено»     │
└───────────────────────┘       └───────────────────────┘
            │                               │
            └───────────────┬───────────────┘
                            ▼
              [СМЕНА СТАТУСА ЗАБЛОКИРОВАНА]
            (удаление клиенту также запрещено)
```

**Жесткие правила переходов:**
1. Любая созданная пользователем заявка автоматически сохраняется со статусом **«Новая»** (`STATUS_NEW`).
2. Перевод в статус **«Принято в работу»** (`STATUS_IN_PROGRESS`) разрешен **только из статуса «Новая»** и требует **обязательного текстового комментария** администратора.
3. Перевод в статус **«Выполнено»** (`STATUS_COMPLETED`) разрешен **только из статуса «Новая»** и требует **обязательного прикрепления файла готового дизайна** (jpg, jpeg, png, bmp до 5 Мб).
4. Любая попытка изменить статус заявки, уже находящейся в статусе «Принято в работу» или «Выполнено», программно блокируется.
5. Клиент имеет право удалить заявку **только в статусе «Новая»**. Если заявка взята в работу или выполнена, удаление запрещено.

# 2. Конфигурация ядра (settings.py) и подсистемы

Файл `design_studio/settings.py` — центральный конфигурационный модуль проекта. Ниже представлен подробный теоретический разбор всех ключевых параметров:

### 1. Системные константы и безопасность:
* `BASE_DIR = Path(__file__).resolve().parent.parent`:  
  Динамически вычисляет абсолютный путь к корневой директории проекта на диске операционной системы. Использование объекта `Path` из стандартной библиотеки `pathlib` гарантирует кроссплатформенную совместимость (пути корректно собираются через оператор `/` как в Windows с обратными слэшами `\`, так и в Linux/macOS с прямыми слэшами `/`).
* `SECRET_KEY = '...'`:  
  Служит криптографической «солью» (seed) для внутренних алгоритмов безопасности фреймворка: генерации CSRF-токенов, цифровой подписи сессионных cookies, генерации токенов сброса паролей и сообщений flash-фреймворка.
* `DEBUG = True`:  
  Флаг режима разработки. При возникновении исключений Django отображает интерактивную страницу отладки со стеком вызовов (Traceback), значениями локальных переменных и выполненными SQL-запросами. Также позволяет встроенному серверу раздавать статические и медиафайлы. В рабочей среде (Production) обязательно устанавливается в `False`.
* `ALLOWED_HOSTS = ['*']`:  
  Список хостов и доменных имен, по которым разрешено обращаться к серверу. Значение `['*']` позволяет беспрепятственно тестировать проект по адресам `localhost`, `127.0.0.1` или любому локальному IP-адресу без ошибок `DisallowedHost (400 Bad Request)`.

### 2. Подключение приложений и кастомная модель пользователя:
* `INSTALLED_APPS`:  
  Реестр активных компонентов системы. Включает 6 стандартных подсистем Django (`admin`, `auth`, `contenttypes`, `sessions`, `messages`, `staticfiles`) и конфигурационный класс нашего приложения `'catalog.apps.CatalogConfig'`.
* `AUTH_USER_MODEL = 'catalog.User'`:  
  **Критически важная настройка!** Указывает Django использовать нашу кастомную модель `User` (унаследованную от `AbstractUser`) вместо стандартной модели аутентификации. Это позволяет хранить обязательное по ТЗ поле `fio` непосредственно в системной таблице пользователей без необходимости создания вторичных связанных таблиц через `OneToOneField`.

### 3. Конвейер Middleware (Промежуточное ПО):
Каждый входящий HTTP-запрос и исходящий HTTP-ответ проходит через конвейер классов-фильтров:
1. `SecurityMiddleware`: базовые заголовки безопасности (X-Content-Type-Options, защита от сниффинга MIME-типов).
2. `SessionMiddleware`: управление серверными сессиями (подключение хранилища `request.session`).
3. `CommonMiddleware`: обработка URL, нормализация слешей (`APPEND_SLASH`).
4. `CsrfViewMiddleware`: валидация токенов безопасности форм от атак межсайтовой подделки запросов.
5. `AuthenticationMiddleware`: привязка текущего авторизованного пользователя к объекту запроса (`request.user`).
6. `MessageMiddleware`: обслуживание временных всплывающих Flash-сообщений.
7. `XFrameOptionsMiddleware`: предотвращение атак кликджекинга (Clickjacking) через запрет встраивания сайта во внешние `<iframe>`.

### 4. Конфигурация шаблонизатора DTL и Context Processors:
Блок `TEMPLATES` подключает движок `django.template.backends.django.DjangoTemplates`.
- `'DIRS': [BASE_DIR / 'templates']`: приоритетный поиск глобальных шаблонов проекта в корневой папке.
- `'APP_DIRS': True`: автоматический поиск шаблонов внутри папок `templates` приложений.
- **Context Processors (Контекстные процессоры):** Функции, автоматически поставляющие глобальные переменные в словарь контекста каждого HTML-шаблона без необходимости ручной передачи из View:
  * `auth`: переменная `{{ user }}` (позволяет проверять `{% if user.is_authenticated %}`).
  * `messages`: переменная `{{ messages }}` (доступ к списку уведомлений).
  * `request`: переменная `{{ request }}` (доступ к текущему URL, параметрам GET/POST).
  * `media`: переменная `{{ MEDIA_URL }}` (базовый путь `/media/` для картинок).

### 5. База данных SQLite:
```python
DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.sqlite3',
        'NAME': BASE_DIR / 'db.sqlite3',
    }
}
```
SQLite — бессерверная, компактная, встраиваемая реляционная СУБД, хранящая всю структуру и данные в одном файле `db.sqlite3`. Идеально подходит для демонстрационного экзамена и учебных проектов: не требует установки и администрирования отдельных служб (PostgreSQL, MySQL), переносится вместе с проектом и поддерживает транзакции ACID и ограничения внешних ключей (`FOREIGN KEY CASCADE`).

### 6. Статика (`STATIC`) против Медиафайлов (`MEDIA`):
В Django строго разграничиваются понятия статики и медиа:
* **Статические файлы (`STATIC`):**  
  * Ресурсы, созданные **разработчиком**: таблицы стилей CSS, JavaScript-скрипты, системные иконки, логотипы интерфейса.  
  * Параметры: `STATIC_URL = '/static/'`, `STATICFILES_DIRS = [BASE_DIR / 'static']`.
* **Медиафайлы (`MEDIA`):**  
  * Бинарные файлы, загружаемые **пользователями** через формы в процессе работы сайта: планы помещений клиентов, готовые визуализации дизайнов.  
  * Параметры: `MEDIA_URL = '/media/'`, `MEDIA_ROOT = BASE_DIR / 'media'`.
  * При `DEBUG = True` раздача медиафайлов настраивается в `urls.py` через директиву `static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)`.

### 7. Архитектура медиа-хранилища: почему `photos/` и `designs/`:
```
media/
├── photos/    <-- Планы помещений и фото комнат от клиентов (до 2 Мб)
└── designs/   <-- Готовые дизайн-проекты и визуализации от администратора (до 5 Мб)
```
Разделение папок обосновано фундаментальным принципом проектирования **Separation of Concerns (Разделение ответственности)**:
1. **Разная природа данных:** Чертежи БТИ и фото без отделки от заказчиков — это *входящие материалы*; визуализации дизайнеров студии — это *готовые результаты*. Сваливать их в один каталог нарушает порядок в файловой системе.
2. **Разные политики безопасности и квот:** К планам применяется лимит 2 Мб, к дизайнам — 5 Мб. Изоляция папок позволяет системному администратору легко настраивать резервное копирование и права доступа.
3. **Наглядность при проверке:** Экзаменатор сразу видит входящие заявки в `photos/` и результаты выполнения студии в `designs/`.

# 3. Теория представлений (Views) и архитектура бизнес-логики

Представления (Views) в Django — это «мозг» веб-приложения. В архитектуре MVT именно View принимает входящий HTTP-запрос, применяет бизнес-правила, взаимодействует с базой данных через модели ORM и возвращает ответ.

### Главная формула любого View в Django:
$$ 	ext{View: } HttpRequest \longrightarrow HttpResponse $$

```python
def my_view(request):
    # 1. Приняли запрос (request)
    # 2. Выполнили логику (БД, валидация, права)
    # 3. Вернули ответ (render или redirect)
    return HttpResponse(...)
```

### Почему FBV (функции), а не CBV (классы)?
В Django есть два подхода к написанию контроллеров:
1. **FBV (Function-Based Views) — представления на функциях:**  
   Каждое действие описывается как обычная Python-функция (`def my_view(request):`).
2. **CBV (Class-Based Views) — представления на классах:**  
   Используется наследование от системных классов (`ListView`, `CreateView`, `DeleteView`).

**Обоснование выбора FBV для проекта «Design.pro»:**
* **100% прозрачность кода:** В CBV вся логика спрятана в глубине наследуемых методов фреймворка (`get_queryset`, `form_valid`, `get_context_data`). На экзамене или защите новичок часто теряется, не понимая, где именно переопределить поведение.
* **Сложная нестандартная логика:** По ТЗ нам требуется перенаправлять пользователей на разные страницы в зависимости от роли (`is_staff`), выполнять двухэтапную смену статусов с разными обязательными полями (комментарий или файл), делать ролевые редиректы. В FBV весь поток выполнения виден сверху вниз от первой до последней строчки.

### Фундаментальные концепции работы View:

#### 1. Разделение запросов `GET` и `POST`:
* **`GET` (Чтение):** Пользователь запрашивает страницу. Функция отдает пустую форму или таблицу с данными. Запрос безопасен (`idempotent`), он не меняет состояние базы данных.
* **`POST` (Запись):** Пользователь отправил заполненную форму с данными. Сервер извлекает данные, валидирует их и вносит изменения в базу данных.

#### 2. Разница между `render()` и `redirect()`: Паттерн PRG (Post/Redirect/Get):
* `render(request, 'template.html', context)`:  
  Компилирует HTML-шаблон с переданным словарем данных и возвращает ответ `200 OK`. Используется при обычных GET-запросах или при возврате формы с ошибками валидации.
* `redirect('route_name')`:  
  Возвращает ответ `302 Found` с заголовком `Location: /target-url/`. Заставляет браузер выполнить новый «чистый» GET-запрос по указанному адресу.
* **Зачем нужен паттерн PRG:** Если после успешного сохранения заявки вызвать `render()`, то при нажатии пользователем клавиши `F5` (Обновить) браузер повторно отправит тот же POST-запрос, создав в базе данных заявку-дубликат. Паттерн PRG (`redirect`) полностью устраняет эту проблему!

#### 3. Загрузка бинарных файлов и `request.FILES`:
Текстовые данные формы попадают в словарь `request.POST`. Однако бинарные потоки файлов (фотографии, планы) передаются браузером отдельно и помещаются в специальный словарь `request.FILES`.  
Поэтому любая форма, принимающая файл, обязана инициализироваться двумя аргументами:
```python
form = ApplicationCreateForm(request.POST, request.FILES)
```
А в HTML-теге `<form>` обязателен атрибут `enctype="multipart/form-data"`.

#### 4. Декораторы доступа и безопасность:
* `@login_required`: блокирует доступ неавторизованным пользователям (гостям), отправляя их на страницу входа.
* `@user_passes_test(is_admin, login_url='login')`: проверяет пользовательскую функцию-предикат. Пропускает только сотрудников (`is_staff`) или суперпользователей (`is_superuser`).

#### 5. Система Flash-сообщений (`django.contrib.messages`):
Поскольку при редиректе (`redirect()`) контекст страницы теряется, Django сохраняет уведомления во временную сессию:
* `messages.success(...)` — зеленая плашка успеха.
* `messages.error(...)` — красная плашка ошибки.
* `messages.info(...)` — синяя информационная плашка.  
При следующем рендеринге страницы базовый каркас `base.html` считывает эти сообщения из сессии и удаляет их после первого показа.

### 4.1. Контроллеры функционала гостя

#### 1. Функция `index(request)` — Главная страница («Витрина студии»)

```python
def index(request):
    in_progress_count = Application.objects.filter(status=Application.STATUS_IN_PROGRESS).count()
    completed_apps = Application.objects.filter(status=Application.STATUS_COMPLETED)\
                         .select_related('category')\
                         .order_by('-created_at')[:4]

    context = {
        'in_progress_count': in_progress_count,
        'completed_apps': completed_apps,
    }
    return render(request, 'index.html', context)
```

##### Логика работы «на пальцах»:
Когда посетитель заходит на сайт `http://localhost:8089/`, браузер выполняет GET-запрос к `index()`.
Функция делает две вещи:
1. Идет в базу данных и считает, сколько сейчас заявок «в работе» (например, 7 штук). Это число выводится крупной цифрой в промо-блоке со счетчиком.
2. Находит все завершенные проекты (статус «Выполнено»), отбирает **ровно 4 самые свежие работы** и подтягивает к ним названия категорий.
3. Упаковывает эти данные в словарь `context` и отправляет в шаблон `index.html`.

##### Построчный разбор:
* `in_progress_count = Application.objects.filter(status=Application.STATUS_IN_PROGRESS).count()`:
  * `filter(...)` — отбирает записи со статусом `'in_progress'`.
  * `.count()` — **критически важная оптимизация!** Он не загружает объекты заявок в оперативную память Python, а заставляет СУБД выполнить быстрый SQL-запрос `SELECT COUNT(*) FROM catalog_application WHERE status = 'in_progress';`. Это работает мгновенно даже при миллионе записей.
* `completed_apps = Application.objects.filter(status=Application.STATUS_COMPLETED)`:
  * Фильтрует только завершенные заявки (`status='completed'`).
* `.select_related('category')`:
  * **Оптимизация жадной загрузки (Eager Loading):** модель `Application` связана с моделью `Category` через внешний ключ `ForeignKey`. Без `select_related` Django при выводе имени каждой категории в цикле шаблона делал бы отдельный SQL-запрос к таблице категорий (проблема N+1 запросов). Метод `select_related` делает один умный SQL `INNER JOIN`, подтягивая категории сразу в основном запросе.
* `.order_by('-created_at')`:
  * Знак минус означает сортировку по убыванию (SQL `ORDER BY created_at DESC`) — самые свежие проекты идут первыми.
* `[:4]`:
  * Срез Python, который Django ORM транслирует в SQL-директиву `LIMIT 4`. Извлекаются ровно 4 строки, что строго соответствует ТЗ («не более 4 последних заявок»).
* `context = {...}`: словарь данных для шаблонизатора DTL.
* `return render(request, 'index.html', context)`: компилирует шаблон и возвращает HTML-страницу со статусом `200 OK`.

#### 2. Функция `register_view(request)` — Регистрация нового пользователя

```python
def register_view(request):
    if request.user.is_authenticated:
        return redirect('cabinet')

    if request.method == 'POST':
        form = UserRegistrationForm(request.POST)
        if form.is_valid():
            user = form.save()
            messages.success(request, f'Регистрация прошла успешно! Добро пожаловать, {user.fio or user.username}!')
            login(request, user)
            return redirect('cabinet')
        else:
            messages.error(request, 'Пожалуйста, исправьте ошибки в форме регистрации.')
    else:
        form = UserRegistrationForm()

    return render(request, 'registration/register.html', {'form': form})
```

##### Логика работы «на пальцах»:
* Если на страницу регистрации случайно зашел уже авторизованный пользователь, система сразу отправляет его в личный кабинет (`redirect('cabinet')`).
* При обычном открытии страницы (`GET`) отдается пустая форма `UserRegistrationForm()`.
* При нажатии кнопки «Зарегистрироваться» (`POST`):
  1. Форма валидирует данные: ФИО только кириллицей, логин только латиницей, email корректный, пароли совпадают, галочка согласия на обработку ПДн установлена.
  2. Если данные корректны: создается запись в таблице `catalog_user` (с хэшированием пароля), выводится приветствие, вызывается `login(request, user)` (автологин без необходимости повторного ввода пароля) и выполняется редирект в личный кабинет.
  3. Если допущены ошибки: форма возвращается обратно пользователю с сохранением введенных данных и красной подсветкой полей с ошибками (`.is-invalid`).

#### 3. Функция `login_view(request)` — Авторизация и ролевая маршрутизация

```python
def login_view(request):
    if request.user.is_authenticated:
        if request.user.is_staff or request.user.is_superuser:
            return redirect('admin_panel')
        return redirect('cabinet')

    if request.method == 'POST':
        form = UserLoginForm(request.POST)
        if form.is_valid():
            user = form.get_user()
            login(request, user)
            messages.success(request, f'Вы успешно вошли как {user.username}!')

            next_url = request.GET.get('next')
            if next_url:
                return redirect(next_url)
            if user.is_staff or user.is_superuser:
                return redirect('admin_panel')
            return redirect('cabinet')
        else:
            messages.error(request, 'Неверный логин или пароль.')
    else:
        form = UserLoginForm()

    return render(request, 'registration/login.html', {'form': form})
```

##### Логика работы «на пальцах»:
* **Ролевой светофор:** Если пользователь уже вошел в систему, он автоматически направляется в свою зону ответственности: администратор — в Панель управления (`/admin-panel/`), обычный клиент — в Личный кабинет (`/cabinet/`).
* При отправке формы (`POST`) вызывается метод `authenticate()`. Если пара логин/пароль верна:
  * Создается сессия пользователя `login(request, user)`.
  * Проверяется параметр `?next=` (если пользователь шел на защищенную страницу до входа, он направляется туда).
  * Если `next` нет: проверяются флаги прав: администратор отправляется в `/admin-panel/`, клиент — в `/cabinet/`.
* При неверном пароле выводится общее сообщение: *«Неверный логин или пароль»* (правило безопасности: не сообщать злоумышленнику, существует ли такой логин в базе).

#### 2. Функция `cabinet_view(request)` — Личный кабинет и фильтрация заявок

```python
@login_required
def cabinet_view(request):
    user_apps = Application.objects.filter(user=request.user).select_related('category')

    total_count = user_apps.count()
    new_count = user_apps.filter(status=Application.STATUS_NEW).count()
    in_progress_count = user_apps.filter(status=Application.STATUS_IN_PROGRESS).count()
    completed_count = user_apps.filter(status=Application.STATUS_COMPLETED).count()

    current_filter = request.GET.get('status', 'all')
    if current_filter in [Application.STATUS_NEW, Application.STATUS_IN_PROGRESS, Application.STATUS_COMPLETED]:
        user_apps = user_apps.filter(status=current_filter)

    user_apps = user_apps.order_by('-created_at')

    context = {
        'applications': user_apps,
        'current_filter': current_filter,
        'total_count': total_count,
        'new_count': new_count,
        'in_progress_count': in_progress_count,
        'completed_count': completed_count,
    }
    return render(request, 'catalog/cabinet.html', context)
```

##### Логика работы «на пальцах»:
1. **Фейсконтроль (`@login_required`):** Гость не может попасть на страницу кабинета; он перенаправляется на `/login/`.
2. **Строгая изоляция данных (`user=request.user`):** Запрашиваются только те заявки, автором которых является текущий вошедший пользователь. Доступ к чужим данным исключен на уровне базового запроса.
3. **Бейджи-счетчики:** Считается количество заявок для каждого статуса и передается в шаблон для отображения на кнопках фильтрации.
4. **Фильтрация по белому списку:** Значение `request.GET.get('status')` сверяется со списком допустимых значений (`new`, `in_progress`, `completed`). Это защищает приложение от вредоносных SQL/URL-манипуляций.
5. **Сортировка:** Заявки сортируются от новых к старым (`-created_at`).

#### 3. Функция `create_application_view(request)` — Оформление заявки клиентом

```python
@login_required
def create_application_view(request):
    if request.method == 'POST':
        form = ApplicationCreateForm(request.POST, request.FILES)
        if form.is_valid():
            application = form.save(commit=False)
            application.user = request.user
            application.status = Application.STATUS_NEW
            application.save()
            messages.success(request, f'Заявка «{application.title}» успешно создана и ожидает обработки!')
            return redirect('cabinet')
        else:
            messages.error(request, 'Пожалуйста, исправьте ошибки в форме заявки.')
    else:
        form = ApplicationCreateForm()

    return render(request, 'catalog/application_form.html', {'form': form})
```

##### Логика работы «на пальцах»:
1. Форма принимает два потока данных: текстовые поля из `request.POST` и бинарный файл плана помещения из `request.FILES`.
2. Валидатор проверяет, что файл не превышает 2 Мб и относится к разрешенным графическим форматам.
3. **Техника `commit=False`:**
   * Метод `form.save(commit=False)` создает объект модели `Application` в памяти Python, **НЕ отправляя SQL-запрос `INSERT` в базу данных**.
   * Зачем это нужно? Поля `user` (автор) и `status` отсутствуют в самой форме (пользователь не должен иметь возможности выбрать чужой ID или установить себе статус «Выполнено»).
   * Сервер сам подписывает автора (`application.user = request.user`) и гарантированно назначает статус «Новая» (`STATUS_NEW`).
4. Вызывается `application.save()` — запись фиксируется в БД, файл сохраняется в `media/photos/`, и клиент перенаправляется в кабинет по паттерну PRG.

#### 4. Функция `delete_application_view(request, pk)` — Безопасное удаление заявки

```python
@login_required
def delete_application_view(request, pk):
    application = get_object_or_404(Application, pk=pk, user=request.user)

    if not application.is_deletable:
        messages.error(
            request,
            'Запрещено! Заявку нельзя удалить, так как её статус уже изменен администратором на «Принято в работу» или «Выполнено».'
        )
        return redirect('cabinet')

    if request.method == 'POST':
        title = application.title
        application.delete()
        messages.success(request, f'Заявка «{title}» была успешно удалена.')
        return redirect('cabinet')

    return render(request, 'catalog/application_confirm_delete.html', {'application': application})
```

##### Логика работы «на пальцах»:
Здесь работают **три эшелона защиты**:
1. **Защита от IDOR (Insecure Direct Object Reference):** Поиск записи ведется строго по двум критериям: `pk=pk` И `user=request.user`. Если злоумышленник попытается удалить чужую заявку №99, введя `/application/99/delete/`, функция вернет `404 Not Found`. Чужая заявка для него не существует.
2. **Проверка конечного автомата:** Свойство `application.is_deletable` проверяет, что статус равен `'new'`. Если заявка уже взята в работу или выполнена, удаление блокируется сообщением об ошибке.
3. **Двухэтапное подтверждение:**
   * `GET`: сервер отображает диалог подтверждения `application_confirm_delete.html`.
   * `POST`: после нажатия кнопки «Да, удалить» выполняется SQL-запрос `DELETE`, удаляется прикрепленный файл плана с диска, и клиент возвращается в кабинет.

# 5. Модели, Django ORM и реляционные связи

Файл: `catalog/models.py`.

### 1. Модель `User` и наследование от `AbstractUser`:
```python
class User(AbstractUser):
    fio = models.CharField(
        max_length=150,
        verbose_name='ФИО',
        help_text='Фамилия, Имя и Отчество'
    )
```
**Почему это лучшее архитектурное решение:**
1. Стандартная модель `django.contrib.auth.models.User` содержит поля `first_name` и `last_name`, но не имеет единого поля `fio`.
2. Альтернативный путь — создание профиля через отношение `OneToOneField(Profile)` — требует постоянных SQL `JOIN` при каждом запросе страницы и усложняет регистрацию (создание двух объектов вместо одного).
3. Наследование от `AbstractUser` сохраняет все встроенные механизмы Django (хэширование паролей, группы, права, флаги `is_staff`, `is_superuser`, дату регистрации) и добавляет поле `fio` прямо в базовую таблицу `catalog_user`.

### 2. Модель `Category` (Категория помещения):
```python
class Category(models.Model):
    name = models.CharField(max_length=100, unique=True, verbose_name='Название категории')
```
* `unique=True`: ограничение уникальности на уровне СУБД SQLite. Гарантирует, что две одинаковые категории не смогут существовать физически.

### 3. Модель `Application` (Заявка на дизайн):
```python
class Application(models.Model):
    STATUS_NEW = 'new'
    STATUS_IN_PROGRESS = 'in_progress'
    STATUS_COMPLETED = 'completed'

    STATUS_CHOICES = [
        (STATUS_NEW, 'Новая'),
        (STATUS_IN_PROGRESS, 'Принято в работу'),
        (STATUS_COMPLETED, 'Выполнено'),
    ]

    user = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE,
        related_name='applications',
        verbose_name='Пользователь'
    )
    category = models.ForeignKey(
        Category,
        on_delete=models.CASCADE,
        related_name='applications',
        verbose_name='Категория'
    )
    title = models.CharField(max_length=200, verbose_name='Название')
    description = models.TextField(verbose_name='Описание')
    photo = models.ImageField(
        upload_to='photos/',
        validators=[validate_photo_file],
        verbose_name='Фото помещения или план'
    )
    status = models.CharField(
        max_length=20,
        choices=STATUS_CHOICES,
        default=STATUS_NEW,
        verbose_name='Статус заявки'
    )
    comment = models.TextField(blank=True, null=True, verbose_name='Комментарий администратора')
    design_image = models.ImageField(
        upload_to='designs/',
        blank=True,
        null=True,
        validators=[validate_design_file],
        verbose_name='Готовый дизайн-проект'
    )
    created_at = models.DateTimeField(auto_now_add=True, verbose_name='Временная метка')
```

#### Ключевые параметры ORM:
* `on_delete=models.CASCADE`: правило ссылочной целостности реляционной БД. При удалении родительской записи (пользователя или категории) СУБД автоматически удаляет все дочерние заявки.
* `related_name='applications'`: имя обратной связи от модели `Category` или `User`. Позволяет вызывать `category.applications.count()` или `user.applications.all()`.
* `auto_now_add=True`: автоматически фиксирует точную дату и время создания записи в БД при первичном вызове `save()`.

#### Вычисляемые свойства модели (Инварианты бизнес-логики):
* `@property def is_deletable(self)`:
  ```python
  return self.status == self.STATUS_NEW
  ```
  Инвариант: заявка доступна для удаления клиентом только тогда, когда ее статус строго равен `STATUS_NEW`.
* `@property def can_change_status(self)`:
  ```python
  return self.status == self.STATUS_NEW
  ```
  Инвариант: администратор может изменить статус заявки только из статуса `STATUS_NEW`.

### 4. Механизм миграций Django:
Миграции — это система версионирования схемы базы данных.
1. `python manage.py makemigrations`:
   * Сравнивает текущие классы в `models.py` с предыдущим состоянием миграций.
   * Генерирует новый Python-файл миграции (например, `0001_initial.py`), описывающий необходимые изменения в виде декларативных операций (`CreateModel`, `AddField`).
2. `python manage.py migrate`:
   * Читает не примененные файлы миграций, транслирует операции в DDL SQL-запросы (`CREATE TABLE`, `CREATE INDEX`, `ALTER TABLE`) для конкретной СУБД (в нашем случае SQLite) и выполняет их в файле `db.sqlite3`.
   * Записывает имя примененной миграции в служебную таблицу `django_migrations`.

# 6. Формы, серверная валидация и информационная безопасность

Файл: `catalog/forms.py`.

### 1. Механизм серверной валидации:
Когда во View вызывается метод `form.is_valid()`, Django запускает трехступенчатый конвейер валидации:
1. **Преобразование типов (`to_python`):** Преобразует строковые данные запроса в соответствующие типы Python (числа, даты, объекты загруженных файлов).
2. **Валидация полей (`clean_<field_name>`):**
   * `clean_fio()`: регулярное выражение `^[А-Яа-яЁё\s\-]+$` проверяет, что ФИО содержит только кириллицу, дефисы и пробелы.
   * `clean_username()`: регулярное выражение `^[a-zA-Z\-]+$` проверяет, что логин состоит только из латиницы и дефисов. Дополнительно проверяется уникальность логина в БД.
   * `clean_name()`: проверяет уникальность имени категории без учета регистра символов (`iexact`).
3. **Общая валидация формы (`clean`):**
   * Сравнивает совпадение полей `password` и `password_confirm`.
   * Проверяет, что отмечен обязательный чекбокс `agree_data_processing` (согласие на обработку персональных данных).
4. Все проверенные и безопасные данные помещаются в словарь `form.cleaned_data`. Если хотя бы одно правило нарушено, форма пополняется словарем `form.errors`.

### 2. Валидация бинарных файлов и Pillow:
Загрузка файлов валидируется на двух уровнях:
1. **Проверка размера и расширения:**
   * `validate_photo_file(file)`: `file.size <= 2 * 1024 * 1024` (до 2 Мб) и расширения `.jpg`, `.jpeg`, `.png`, `.bmp`.
   * `validate_design_file(file)`: `file.size <= 5 * 1024 * 1024` (до 5 Мб) и расширения `.jpg`, `.jpeg`, `.png`, `.bmp`.
2. **Проверка целостности графического потока байтов через библиотеку Pillow:**
   Поле `ImageField` автоматически использует библиотеку Pillow: при сохранении файла вызывается `Image.open(file)` и `image.verify()`. Если злоумышленник переименует исполняемый PHP-скрипт или вирус `evil.php` в `evil.png`, Pillow обнаружит отсутствие корректных заголовков растрового изображения (JPEG SOI маркер, PNG сигнатура) и выбросит исключение валидации, предотвратив выполнение шелла на сервере.

### 3. Информационная безопасность веб-приложения:
* **Защита от CSRF (Cross-Site Request Forgery):**
  * Тег `{% csrf_token %}` внедряет в каждую форму скрытый криптографический токен.
  * `CsrfViewMiddleware` сверяет значение из формы со значением в защищенной cookie пользователя. При несовпадении запрос отвергается с кодом `403 Forbidden`.
* **Защита от XSS (Cross-Site Scripting):**
  * Шаблонизатор DTL по умолчанию выполняет автоматическое экранирование всех выводимых переменных (`{{ var }}`). Опасные символы `< > " ' &` преобразуются в безопасные HTML-сущности `&lt; &gt; &quot; &#39; &amp;`. Попытка внедрить `<script>alert(1)</script>` просто отобразится как безобидный текст.
* **Защита от IDOR (Insecure Direct Object References):**
  * При удалении заявки обращение к модели идет с обязательной привязкой к автору: `get_object_or_404(Application, pk=pk, user=request.user)`. Пользователь принципиально не может воздействовать на чужие записи, меняя цифры ID в строке браузера.
* **Криптографическое хэширование паролей:**
  * Пароли пользователей никогда не хранятся в открытом виде.
  * Метод `user.set_password()` использует промышленный алгоритм **PBKDF2 с HMAC-SHA256**, 720 000 итерациями и индивидуальной криптографической солью, что делает подбор паролей по радужным таблицам (Rainbow Tables) математически невозможным.

* `{% extends 'base.html' %}`: указывает DTL, что шаблон наследует скелет базового макета.
* `{% block content %}`: определяет посадочное место, куда дочерний шаблон помещает свою уникальную разметку.

### 2. Серверная подсветка невалидных полей:
При возникновении ошибок валидации:
```html
<input type="text" name="fio" class="form-input {% if form.fio.errors %}is-invalid{% endif %}" value="{{ form.fio.value|default:'' }}">
{% if form.fio.errors %}
    <div class="field-error">{{ form.fio.errors.0 }}</div>
{% endif %}
```
* Класс `is-invalid` окрашивает границу поля в красный цвет (`#cc0000`).
* Блок `field-error` выводит точный текст ошибки непосредственно под полем.
* Конструкция `value="{{ form.fio.value|default:'' }}"` сохраняет введенный пользователем текст, избавляя от необходимости повторного ввода.

### 3. Автономный интерфейс без Bootstrap:
* **Отказ от внешних CDN:** Проект полностью автономен. В условиях демонстрационного экзамена компьютеры часто отключены от интернета — чистый локальный CSS (`static/css/style.css`) гарантирует идеальную верстку в любых условиях.
* **Нативный HTML5 `<dialog>` API:**  
  Вместо 150+ Кб библиотек Bootstrap JS и jQuery диалоговые окна реализованы через встроенный стандартный тег HTML5 `<dialog>`:
  * Открытие: `document.getElementById('dialogId').showModal()` (автоматически создает темную модальную подложку `::backdrop` и блокирует прокрутку).
  * Закрытие: `this.closest('dialog').close()`.

# 8. Тестирование, развертывание и эксплуатация

Файл: `catalog/tests.py`.

### 1. Архитектура автоматизированного тестирования:
* Тесты наследуются от стандартного класса `django.test.TestCase`.
* **Изоляция данных:** При запуске `python manage.py test` Django создает временную тестовую базу данных в памяти. Все операции создания, изменения и удаления записей изолированы и не затрагивают рабочий файл `db.sqlite3`. После прогона тестов тестовая БД бесследно уничтожается.
* **Виртуальный HTTP-клиент (`Client`):** Метод `self.client.post()` и `self.client.get()` симулирует реальные HTTP-запросы браузера с поддержкой cookies, сессий и заголовков.
* **Генерация тестовых файлов в памяти:**  
  С помощью модулей `io.BytesIO` и `PIL.Image` создаются виртуальные растровые изображения `SimpleUploadedFile('test.png', ...)` без необходимости засорять жесткий диск тестовыми файлами.

#### Пакет из 6 сквозных тестов проверяет:
1. `test_registration_validation`: отклонение латиницы в ФИО, кириллицы в логине, несовпадения паролей и успешную регистрацию.
2. `test_create_application_validation`: блокировку неграфических файлов (.txt) и корректное создание заявки со статусом «Новая».

4. `test_admin_status_transitions`: обязательность комментария при взятии заявки в работу и запрет на повторную смену статуса.
5. `test_category_cascade_delete`: автоматическое каскадное удаление всех связанных заявок при удалении категории.
6. `test_main_page_counter_and_limit`: точность счетчика заявок в работе и жесткое ограничение ровно в 4 выполненных проекта на главной.

# 9. Полный сводный каталог вопросов и эталонных ответов для защиты (ТОП-28)

1. **Вопрос:** Что такое MVT в Django и чем отличается от MVC?  
   **Ответ:** MVT — это разновидность MVC. Model отвечает за базу данных и ORM, View играет роль Контроллера (обрабатывает запрос и применяет логику), а Template выполняет роль View (отображает данные в HTML).

2. **Вопрос:** Почему мы создали кастомную модель `User` через `AbstractUser`?  
   **Ответ:** Это позволило добавить обязательное поле ФИО в саму таблицу пользователей. Это быстрее и архитектурно правильнее, чем делать дополнительную таблицу `Profile` через `OneToOneField`, требующую постоянных SQL `JOIN`.

3. **Вопрос:** Как обеспечивается уникальность логина?  
   **Ответ:** На уровне БД ограничением `UNIQUE` поля `username` и на уровне формы в методе `clean_username()`.

4. **Вопрос:** Где и как проверяется ограничение размера фото в 2 МБ?  
   **Ответ:** В функции-валидаторе `validate_photo_file` в `models.py`. Она проверяет `file.size > 2 * 1024 * 1024` и расширение файла. При несоответствии выбрасывается `ValidationError`.

5. **Вопрос:** Что происходит с заявками при удалении категории?  
   **Ответ:** В модели `Application` в поле `category` указано `on_delete=models.CASCADE`. База данных SQLite автоматически каскадно удаляет все связанные с этой категорией заявки.

6. **Вопрос:** Почему обычный пользователь не может удалить заявку в статусе «Принято в работу»?  
   **Ответ:** В представлении `delete_application_view` проверяется свойство `application.is_deletable` (`status == 'new'`). Если статус изменен администратором, операция программно пресекается.

7. **Вопрос:** Как защищено удаление от подмены `id` в URL?  
   **Ответ:** Запрос выполняется через `get_object_or_404(Application, pk=pk, user=request.user)`. Запрос жестко привязан к текущему пользователю; попытка ввести чужой ID вернет ошибку 404 (IDOR-защита).

8. **Вопрос:** Как устроен счетчик заявок в работе на главной?  
   **Ответ:** `Application.objects.filter(status='in_progress').count()` выполняет быстрый SQL-запрос `SELECT COUNT(*)`, не выгружая объекты в память.

9. **Вопрос:** Как ограничивается вывод не более 4 выполненных заявок на главной?  
   **Ответ:** Срез `[:4]` в QuerySet транслируется в SQL-директиву `LIMIT 4`.

10. **Вопрос:** Почему со статуса «В работе» или «Выполнено» нельзя сменить статус?  
    **Ответ:** Согласно ТЗ, смена разрешена только из статуса «Новая». В методе контроллера стоит условие `if application.status != Application.STATUS_NEW: return redirect(...)`.

11. **Вопрос:** Зачем нужен `{% csrf_token %}` в формах?  
    **Ответ:** Для защиты от межсайтовой подделки запросов (CSRF). Django сверяет криптографический токен формы с токеном в сессии.

12. **Вопрос:** Что делает `select_related('category')` в запросах?  
    **Ответ:** Это жадная загрузка (Eager Loading), которая объединяет таблицы через SQL `INNER JOIN` и решает проблему «N+1 запросов».

13. **Вопрос:** Как разграничены права доступа гостей, клиентов и администратора?  
    **Ответ:** Гости проверяются через `not user.is_authenticated`, клиенты — через `@login_required`, администратор — через `@user_passes_test(is_admin)` с проверкой флагов `is_staff` / `is_superuser`.

14. **Вопрос:** Как работает фильтрация по статусу в кабинете?  
    **Ответ:** Через GET-параметр `?status=...`. Контроллер считывает параметр `request.GET.get('status')` и применяет `.filter(status=current_filter)`.

15. **Вопрос:** Почему админка доступна по адресу `/superadmin`?  
    **Ответ:** Это прямое требование ТЗ раздела "Инструкция для студента". В `urls.py` мы переопределили путь на `path('superadmin/', admin.site.urls)`.

16. **Вопрос:** В каком виде хранятся пароли в базе?  
    **Ответ:** В виде криптографического хеша алгоритма PBKDF2 с солью, сформированного методом `user.set_password()`.

17. **Вопрос:** Как Django раздает загруженные картинки при разработке?  
    **Ответ:** С помощью функции `static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)` в `urls.py` при `DEBUG = True`.

18. **Вопрос:** В чем разница между `makemigrations` и `migrate`?  
    **Ответ:** `makemigrations` создает файл описания изменений схемы, а `migrate` применяет их к таблицам базы данных.

19. **Вопрос:** Зачем папки в media разделены на `photos/` и `designs/`?  
    **Ответ:** Для архитектурного разделения входящих исходников клиентов (до 2 Мб) и результатов работы дизайнеров студии (до 5 Мб) по принципу Separation of Concerns.

20. **Вопрос:** Как подсвечиваются поля с ошибками при регистрации?  
    **Ответ:** В шаблоне проверяется `{% if form.field.errors %}` и тегу `<input>` присваивается класс `is-invalid`, а под ним выводится блок с текстом ошибки.

21. **Вопрос:** Что такое `commit=False` в `form.save(commit=False)`?  
    **Ответ:** Создает экземпляр модели в памяти, не сохраняя его сразу в БД, чтобы мы могли программно привязать пользователя (`user=request.user`) и статус («Новая»).

22. **Вопрос:** Зачем нужен файл `manage.py`?  
    **Ответ:** Это скрипт командной строки для управления проектом (запуск сервера, миграции, тесты).

23. **Вопрос:** Что такое `related_name` во внешнем ключе?  
    **Ответ:** Это имя обратной связи от целевой модели к исходной (например, `category.applications.all()`).

24. **Вопрос:** Как работает библиотека Pillow в проекте?  
    **Ответ:** Pillow верифицирует графический поток байтов при сохранении `ImageField`, гарантируя, что под видом картинки не загружен исполняемый файл или скрипт.

25. **Вопрос:** Как запустить сервер на требуемом порту 8089?  
    **Ответ:** Командой `python manage.py runserver 8089`.

26. **Вопрос:** Почему в проекте был выполнен полный отказ от Bootstrap в пользу чистого CSS?  
    **Ответ:**  
    1) **Автономность и надежность:** На демонстрационном экзамене рабочие станции изолированы от интернета. Чистый локальный CSS гарантирует 100% работу офлайн без зависимости от CDN.  
    2) **Скорость:** Исключение Bootstrap сэкономило сотни килобайт ненужного кода.  
    3) **Чистота стандартов:** Демонстрирует комиссии глубокое владение базовыми стандартами веба (Flexbox, Grid, CSS Variables).

27. **Вопрос:** Как работают модальные окна без использования JavaScript-библиотеки Bootstrap?  
    **Ответ:** Использован нативный стандартный тег HTML5 `<dialog>`. Он поддерживается всеми современными браузерами и предоставляет встроенные методы API: `dialog.showModal()` для открытия с автоматической модальной блокировкой фона (`::backdrop`) и `dialog.close()` для закрытия.

28. **Вопрос:** Как архитектурно структурирован файл стилей `style.css`?  
    **Ответ:** Файл логически разбит на модули: дизайн-токены `:root`, сброс стилей (Reset), шапка и навигация, кнопки и фильтры, Flash-сообщения (Alerts), карточки проектов, таблицы со статусными бейджами, формы с подсветкой ошибок (`.is-invalid`), модальные окна `<dialog>` и прижатый подвал.
